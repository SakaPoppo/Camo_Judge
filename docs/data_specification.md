# データ仕様書 — 画像収集・品質・メタデータ

- **版**：Draft v0.3
- **更新日**：2026-11-17
- **状態**：画像カテゴリ、収集・品質・保存、DB基本方針は確定。前処理とDB詳細設計は未決定

## 1. 目的

迷彩と背景の色彩特徴量を、後から再現・比較・追跡できる画像データセットとして整理します。

## 2. 画像構成【確定】

| 役割 | 分類 | 各分類の画像数 | 合計 |
|---|---:|---:|---:|
| 迷彩 | 9種類 | 1枚 | 9枚 |
| 背景 | 6タイプ × 2植生状態 | 3枚 | 36枚 |
| **合計** | | | **45枚** |

- 比較の組み合わせ：9 × 36 = **324組**
- 324組は**独立した観測数ではありません**。同じ迷彩画像や背景画像を再利用します。
- 迷彩ごとに1画像しかないため、同じ迷彩の撮影差はMVPでは評価できません。

## 3. 背景分類【確定】

### 3.1 背景タイプ

フィールド全体を森林・市街地などで分類せず、サバイバルゲームで実際に身を隠す場所の植生や背景を基準に分類します。市街地・建造物は今回のMVPでは対象外です。

| ID | 背景タイプ |
|---|---|
| BG01 | 笹・ササ藪 |
| BG02 | 低木・灌木の茂み |
| BG03 | 高草・ススキ |
| BG04 | シダ・低い下草 |
| BG05 | 木の根元・樹幹 |
| BG06 | ツル植物・絡み合った藪 |

### 3.2 植生状態

| 状態 | 定義 |
|---|---|
| `green` | 緑葉が多く、植生が繁茂している状態 |
| `dry` | 枯葉・枯草・茶色系の植生が目立つ状態 |

- `green` / `dry` は季節そのものではなく、画像に写っている植生状態を示します。
- 撮影年月日や季節は、別途メタデータとして記録します。
- 雨による濡れ具合を意味するWet / Dryとは区別します。
- すべての背景タイプで両状態を収集する計画ですが、画像の入手可能性と分類の妥当性はデータ収集時に確認します。

## 4. 迷彩パターン【確定】

| ID | 迷彩パターン | 分類 |
|---|---|---|
| CM01 | MultiCam Tropic | Green系 |
| CM02 | MultiCam Original | 汎用系 |
| CM03 | A-TACS FG | Green系 |
| CM04 | A-TACS AU | Dry系 |
| CM05 | Tiger Stripe（緑系） | Green系 |
| CM06 | Desert Tiger Stripe | Dry系 |
| CM07 | 陸上自衛隊迷彩2型 | 独立比較 |
| CM08 | OD（単色） | 単色比較 |
| CM09 | PenCott GreenZone | Green系 |

Green系・Dry系・汎用系などは分析用の分類であり、実測した性能評価ではありません。

### 4.1 採用時の注意

- MultiCam Aridは採用せず、MultiCam Originalを採用します。
- PenCott BadLandsは採用せず、PenCott GreenZoneを採用します。
- Tiger Stripeの具体的なバリエーションや製品は画像収集時に確定します。
- A-TACS FG / AUとFG-X / AU-Xを混同しないよう、画像の名称と出典を確認します。

### 4.2 選定方針

1. サバイバルゲームでの知名度や使用実績があるパターンを含める。
2. Green系・Dry系の両方を比較する。
3. 同系列の異なるバリエーションを比較する。
4. 日本の森林環境を想定した比較対象として陸上自衛隊迷彩2型を含める。
5. 模様のない比較対象としてOD単色を含める。
6. 色彩だけでなく、模様の形状や細かさの違いも考慮する。

ODと柄物の比較だけでは色彩や明暗などの条件も同時に異なるため、模様単独の効果や因果関係は断定しません。

## 5. 画像収集・採用基準【確定】

### 5.1 画像収集方法

- 公開画像と自撮り画像を併用する。
- 同じ背景タイプ・植生状態ごとに3枚を収集し、できるだけ別の撮影シーンを使用する。
- 公開画像と自撮り画像はメタデータで区別する。
- 公開画像は出典URLと利用条件を記録する。
- 撮影条件が不明な公開画像は不明値として記録し、推測で補完しない。

### 5.2 背景画像の撮影・構図

| 項目 | 確定内容 |
|---|---|
| 基準撮影距離 | 約5m |
| 許容距離 | 3〜10m |
| 距離の基準 | カメラから最初の主要な植生まで |
| カメラの高さ | 地面から約1.5m |
| 撮影角度 | 原則水平・正面寄り |
| 画角 | 標準画角を優先 |
| 構図 | 人が隠れる想定位置を中央付近に配置 |
| 背景占有率 | 対象植生が画面の約70%以上 |
| 除外する要素 | 目立つ人物・人工物・不要な背景など |

- 5m前後の画像を優先しつつ、3〜10mの範囲を許容する。
- 撮影距離が不明な公開画像は、それだけを理由に除外しない。
- 植物の接写より、実際に隠蔽場所を観察する視点の画像を優先する。
- 自然に発生する木陰や明暗の違いは分析対象となるため、一律には除外しない。
- 撮影距離の違いがテクスチャやエッジ密度の分析に影響する可能性を記録する。

### 5.3 画像品質基準

| 項目 | 条件 |
|---|---|
| 最低解像度 | 原則として短辺1024px以上 |
| 画像形式 | JPEG / PNG |
| 分析用色空間 | sRGB |
| ピント | 対象の葉・枝・模様が識別可能 |
| 色補正 | 強い加工・フィルターを避ける |
| 明暗 | 極端な白飛び・黒つぶれを避ける |
| 重複 | 同一画像や単純な切り抜き違いを独立した画像として扱わない |

撮影条件の完全な統一よりも、一定の品質を満たしながら植生の多様性を確保するバランス重視の方針とします。明らかな色かぶり、過度な加工、品質不良は除外します。

迷彩画像は、生地やパターンが十分な面積で見え、対象の模様を識別できるものを使用します。ロゴ、タグ、周囲の背景などが多い場合は、原本を保持したうえで対象領域を切り出し、加工条件を記録します。

### 5.4 色空間の管理

- 原本画像は色空間を変更せず保持する。
- 分析用画像はsRGBに統一する。
- ICCプロファイルが存在する場合は確認・記録する。
- sRGB以外の画像は、確認できたICCプロファイルを使用して色管理変換する。
- ICCプロファイルが不明な場合は不明として記録し、推測で確定しない。
- 自動ホワイトバランス・彩度補正と、色空間の変換を区別する。
- HSV・Labなどへの分析用変換は、適切に色管理した画像を対象にする。

### 5.5 品質判定

| 判定 | 意味 |
|---|---|
| `accepted` | 採用 |
| `pending` | 追加確認が必要 |
| `rejected` | 除外 |

- 保留・除外には理由を記録する。
- 分析には原則として `accepted` の画像のみを使用する。
- 採用後に分類・品質判定を変更した場合も、変更理由を追跡できるようにする。
- 分析結果を見た後で、都合の悪い画像を恣意的に除外しない。
- 画像品質と、利用・再配布の権利確認は別々に管理する。

## 6. データ管理方針【確定】

- 主データ管理にはPostgreSQLを採用する。
- CSVは主たるデータ管理方法にせず、分析結果の共有・確認・再現に必要なエクスポート形式として利用する。
- Python、SQL、Pandasからの参照・分析を想定する。
- 将来、画像特徴量とWebクイズの回答結果を画像IDでJOINできる構成を想定する。
- 画像本体はDBに格納せず、識別情報、分類、出典、品質判定、保存先、加工履歴を管理する。

### 6.1 管理する情報の候補

以下は管理対象となる情報の候補であり、正式なカラム名・型・必須条件ではありません。

| 情報 | 内容 |
|---|---|
| 画像ID | 分類から独立した一意な識別子 |
| 画像の役割 | 迷彩画像 / 背景画像 |
| 迷彩分類 | 迷彩パターン、系列、バリエーション |
| 背景分類 | 背景タイプ、`green` / `dry` |
| 収集方法 | 公開画像 / 自撮り画像 |
| 出典・権利 | 出典URL、撮影者、利用・再配布条件 |
| 撮影情報 | 撮影日、フィールド名、距離、カメラ高、画角、季節、照明など |
| 品質判定 | `accepted` / `pending` / `rejected`、判定理由、変更理由 |
| 色管理 | ICCプロファイル、確認状況、変換内容 |
| 加工情報 | 切り抜き、リサイズ、色空間変換、加工条件、バージョン |
| 備考 | 不明値、品質上の注意、分類上の補足 |

正式なカラム名、データ型、NULLの扱い、制約、命名規則は詳細設計で決定します。不明な撮影条件やICCプロファイルは推測で補完しません。

## 7. 画像ファイル保存方針【確定】

- 画像ファイルはローカルに保存し、画像本体をDBへ格納しない。
- 原本画像と加工済み画像を必ず分離する。
- 原本画像は上書き・加工せず、加工条件が変わっても原本から再処理できるようにする。
- DBにはローカル環境固有の絶対パスではなく、相対パスなど移行しやすい保存先情報を記録する。
- 1つの画像に複数の加工済みファイルを紐づけられる構成を想定する。
- 将来のWebクイズとの連携を考慮するが、クイズ画像の縦横比・解像度・表示サイズは今回決めない。

```text
data/
├── raw/           # 原本画像
└── processed/     # 分析用加工画像
```

ローカル画像のバックアップ方法と将来のクラウド移行方法は未決定です。画像ファイル、秘密情報、権利上公開できない情報をGitHubへ誤って追加しないよう、Git管理対象を詳細設計で定めます。今回はディレクトリの新規構築やGit管理設定の実装は行いません。

## 8. PostgreSQL基本設計【確定範囲】

### 8.1 4テーブルの役割

| テーブル | 役割 |
|---|---|
| `camouflage_patterns` | 迷彩パターン9種類のマスターデータを管理する |
| `background_types` | 背景6タイプのマスターデータを管理する |
| `images` | 画像ごとの役割、分類、撮影条件、出典、品質判定などを管理する |
| `image_files` | 原本・加工済みファイルの保存先、形式、サイズ、色空間、ハッシュ、加工バージョンなどを管理する |

`green` / `dry` は背景タイプではなく、`images` に属する画像ごとの植生状態として扱います。迷彩画像と背景画像では異なる分類情報を持つことを考慮します。

### 8.2 テーブル間の関係

- `camouflage_patterns` と `images`：1対多
- `background_types` と `images`：1対多
- `images` と `image_files`：1対多

`images` の各レコードは迷彩または背景のいずれかの役割を持ちます。画像IDは分類から独立した一意な識別子とし、変更・再利用しない方針です。正式なID形式は詳細設計で決定します。

### 8.3 DB詳細設計で決めること

- SQLAlchemyモデルとAlembicマイグレーション

## 9. 画像を比較する際の単位

- **画像単位**：各画像から色彩やテクスチャの特徴量を1セット抽出
- **ペア単位**：迷彩1枚 × 背景1枚を組み合わせて距離を算出
- **背景タイプ・植生状態単位**：各組み合わせに属する3枚について集計
- **背景タイプ単位**：必要に応じて `green` / `dry` を区別したまま比較する

背景タイプと植生状態を識別できる設計は確定していますが、3枚の集計方法と順位付けルールは未決定です。
