# GitHub開発フロー

## 目的

個人開発で作業の目的と判断を追跡できるようにしつつ、管理作業を必要最小限に保ちます。

## 基本ルール

- 原則として `1 Issue = 1ブランチ = 1 Pull Request` とします。
- `main` への直接変更を避けます。
- Issueに関連する変更のみを実施し、別の課題は別Issueへ分けます。
- Issueの作業内容が完了してからマージします。
- PRには `Closes #Issue番号` を記載します。
- 原則としてSquash mergeを使用します。
- Codexはユーザーの明示的な許可なくマージしません。

小さな修正ではIssueやPRの説明を短くして構いません。不要なサブタスクや承認手順は増やさず、変更理由と確認結果だけは残します。

## 開発の流れ

### 1. Issue作成

目的に合うIssue Formを選び、概要または目的、作業内容、完了要件を記載します。必要に応じて備考へ関連資料や制約を残します。仕様判断が必要な場合は、確定・暫定・未決定のどれに当たるかを確認します。

### 2. ブランチ作成

最新の `main` から、Issue番号を含むブランチを作成します。命名は [命名規則](naming_conventions.md) に従います。

### 3. 実装・調査

Issueの範囲内で変更します。仕様と矛盾した場合や未決定事項の判断が必要になった場合は、推測で進めずユーザーへ報告します。

### 4. テスト・セルフレビュー

変更内容に応じたテストや確認を行い、差分に不要な変更、秘密情報、権利上問題のある画像がないか確認します。分析・調査では、入力データ、条件、手順、結果の保存先を記録します。

### 5. PR作成

PRテンプレートに沿って概要、変更事項、関連Issue、チェックを記載し、補足や注意点がある場合は最後の備考へ記載します。未確認の項目にはチェックを付けません。

### 6. マージ前チェック

[マージ前チェックリスト](merge_checklist.md)を確認し、Issueの作業内容と仕様書・実装の整合性を見直します。

### 7. Squash merge

ユーザーの許可を得たうえでSquash mergeします。Squash後のコミットメッセージはPRタイトルと整合させます。

### 8. Issueクローズ

PRに `Closes #Issue番号` が記載されていれば、デフォルトブランチへのマージ時に自動クローズされます。自動クローズされない場合は、成果物へのリンクとともに完了を記録します。

## 仕様変更の扱い

- **確定**：承認なしに変更しません。
- **暫定**：候補として扱い、確定した前提で実装しません。
- **未決定**：推測で決めず、選択肢と推奨案を提示して確認します。

仕様変更が承認された場合は、関連する仕様書を同じ変更内で更新します。古い記述と新しい記述を矛盾したまま残しません。

## 将来のCI導入予定

Pythonの実行環境とテスト構成が確定した段階で、次を検討します。現時点ではGitHub Actionsを作成しません。

- RuffによるLint
- pytestによる自動テスト
- PR作成・更新時のCI実行
- CI成功をマージ条件に設定
